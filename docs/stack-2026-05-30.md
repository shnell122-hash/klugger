## 7. Ventajas del sistema actual

1. **Router IA multi-proveedor resiliente**: 5 tiers con fallback automático entre 6 backends (Groq, Gemini, DeepSeek, Claude, OpenAI, OpenRouter) — si un proveedor cae, el sistema sigue operando.
2. **Claude Proxy centralizado**: `claude-proxy-max` (Opus) + 4 instancias `claude-proxy-pro` (Sonnet) garantizan que la API key de Anthropic nunca queda expuesta en el código del agente.
3. **5 agentes especializados en v60**: `document_intelligence`, `graph_agent`, `materialidad_agent`, `vision_agent`, `bulk_generator` — capacidades jurídicas avanzadas sin prompt genérico.
4. **Diseño de sistema oscuro consistente**: `prose-vilar` + `prose-vilar-doc` en CSS + Tailwind — los artefactos generados se renderizan nativamente con el UI del cliente sin iframes.
5. **Socket.io en tiempo real**: Los usuarios ven artefactos y tareas llegar sin recargar — polling HTTP confiable bajo werkzeug threading mode.
6. **Multi-rol/multi-org completo**: `master → sub_master → org_admin → user` — jerarquía de permisos real implementada en Flask sessions con validación en cada endpoint.
7. **Skills de agente autónomos**: `/ejecutar` puede implementar un ítem de roadmap completo (backend + frontend + deploy + smoke test) sin intervención humana.
8. **Costo operativo mínimo**: Groq (Tier 0) y DeepSeek (Tier 2) son prácticamente gratuitos para tareas masivas — Claude solo se usa para lógica crítica.

## 8. Debilidades y deuda técnica

1. **v60-testing con 126 reinicios**: Flask en modo threading werkzeug es inestable bajo carga — indica que hay crashes silenciosos, probablemente por timeout/memory en requests largos de IA.
2. **Swap al 83% de uso**: El host comparte recursos entre 30+ procesos PM2. Bajo carga concurrente, puede haber OOM kills. No hay alertas configuradas.
3. **Sin CI/CD automatizado**: Cada deploy requiere intervención manual del agente (git pull → copyFileSync → pm2 restart → next build ~2 min). Un error humano puede romper producción.
4. **Sin tests automatizados**: No existe pytest para el backend ni Playwright para el frontend. El único safety net es el smoke test manual de 12 endpoints.
5. **Archivos subidos en filesystem local**: `/uploads/` vive en el mismo disco del servidor. Sin backups, sin CDN, sin deduplicación cross-server. Un disco lleno rompe todo.
6. **SQL raw sin ORM**: Queries con `mysql-connector-python` directamente — sin migraciones versionadas, sin type safety, sin protection automático contra N+1 queries.
7. **v59 frontend es HTML monolítico**: `index.html` ~5000+ líneas mezcla JS/CSS/HTML sin modularidad. Imposible hacer code splitting, lazy loading o tests de componentes.
8. **Sin observabilidad**: No hay Sentry para errores, no hay Prometheus/Grafana para métricas. Los fallos se detectan solo cuando un usuario reporta o el smoke test falla.
9. **Session store en filesystem**: `/tmp/vilar-v60-sessions` — si el servidor se reinicia, todas las sesiones se pierden. No es problema en desarrollo pero sí en producción.
10. **La brecha v59/v60 es grande**: v60 tiene 5 agentes, LiteLLM router, Next.js y 20+ commits de mejoras que v59 no tiene. Mantener dos versiones duplica la deuda de mantenimiento.
